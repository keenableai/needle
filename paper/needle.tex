\begin{abstract}
\needle measures web search APIs on five tasks: news, finance, papers,
law and rare-word queries. It draws queries and reference answers from
public sources on each run, except for a fixed rare-query stream, and
scores the returned titles, URLs and snippets. We study 26 API
configurations. Across 12 days with all 21 main engines present, paired
tests separate 178 of 210 engine pairs after Bonferroni adjustment.
Title queries hide large differences: 23 configurations achieve scholar
recall@10 of .71--.98 from titles, but .08--.72 from body keywords.
Blinded LLM raters broadly agree with the relevance judge; no human
audited the scorers. Code, data and dashboard
are public; links are withheld for review.
\end{abstract}

\section{Introduction}

An agent can read a paper only if its search API finds it. Over 30 days,
Keenable found papers from body-keyword queries such as ``gap rent
regularity'' with recall@10 .72; ChatGPT search reached .08. Both exceeded
.80 on title queries (Figure~\ref{fig:results}a). The choice of query can
therefore hide or expose a large retrieval gap.

\needle tests the search API alone: one query in, up to $k$ results out,
scored on the title, URL and snippet an agent receives. It does not score
the agent's final answer, as BrowseComp does \citep{wei2025browsecomp}, or
hold the corpus fixed, as FreshStack does \citep{thakur2025freshstack}.
Fresh queries and reference answers limit dependence on a fixed test set,
which can leak into training data \citep{sainz2023trouble,balloccu2024leak},
though registry facts and rare queries can repeat.

The benchmark combines five tasks, automatic scoring and a pooled
ceiling: the best results found by any tested configuration. We report:
\begin{itemize}[nosep,leftmargin=1.2em]
\item Results for 26 configurations, including paired tests on 12.4k
  query-runs shared by the 21 main engines.
\item Paired scholar query types that expose differences between title
  and full-text retrieval.
\item Checks of the judge, matchers, ceiling and failure rules, with
  samples and labels for readers to inspect.
\end{itemize}

\section{Related Work}
\label{sec:related}

\textbf{Live and API benchmarks.} LiveBench and LiveSearchBench draw new
items from dated sources but score model answers
\citep{white2025livebench,zhou2026livesearchbench}. BrowseComp scores agents
end to end \citep{wei2025browsecomp}; FreshStack and BrowseComp-Plus fix
the corpus to isolate retrieval
\citep{thakur2025freshstack,chen2026browsecompplus}. API comparisons use
static questions under one agent \citep{selvam2026search,aa2026searchindex},
while web engine audits use fixed query sets
\citep{lewandowski2015evaluating,kirsten2026characterizing}.

\textbf{Scorers and tasks.} LLM assessors and simulated known-item queries
can reproduce system rankings
\citep{thomas2024llms,upadhyay2025largescale,azzopardi2007simulated,he2025totelicitation}.
Domain benchmarks cover literature, caselaw and finance search
\citep{ajith2024litsearch,hou2025clerc,hu2026finsearchcomp}; full text helps
retrieval beyond abstracts \citep{lin2009fulltext}. \needle combines these
methods with fresh queries and isolated API scoring. Its contribution is
the live comparison and paired diagnostics across APIs, not a new scorer.

\section{The Benchmark}
\label{sec:bench}

A \emph{configuration} is an API at one setting. We test 26 configurations
from 20 vendors, including five mode variants, and call each an
\emph{engine}. A \emph{query-run} is one query issued in one run.
Appendix~\ref{app:examples} gives the workflow, request settings and run
counts.

\subsection{Queries}

\textbf{News.} Each hour an LLM writes 20 event queries from news feeds
and Google Trends, rejecting evergreen items.
\textbf{Finance.} Queries ask for company facts from Wikidata
\citep{vrandecic2014wikidata} and GLEIF, quarterly 10-Q figures from SEC
XBRL, or filings by description.
\textbf{Scholar.} Each recent arXiv or Europe PMC \citep{europepmc2015}
paper yields four paired known-item queries \citep{azzopardi2007simulated}:
its normalized \emph{title}; \emph{body keywords} for a detail absent from
title and abstract; a \emph{body question} about that detail; and a
\emph{tip-of-tongue} description \citep{arguello2021tot} without names or
exact values. All four must pass the filters.
\textbf{Legal.} CourtListener opinions yield caption queries; eCFR
sections yield queries based on verbatim spans. Filters reject citation
leaks.
\textbf{Rare.} We sample a fixed public stream of English agent queries
containing rare words \citep{ning2026agentic,li2026openresearcher,zhou2026lrat}.
Appendix~\ref{app:leak} gives filters and examples.

At least half of legal queries and finance money and filing queries carry
quotes, \texttt{site:}, \texttt{after:} or \texttt{before:}. The client maps
operators to native filters where available; Appendix~\ref{app:ops}
gives the mappings and paired tests of operator effects.

\subsection{Scores}
\label{sec:scoring}

\textbf{News and rare.} GPT-6 rates each distinct result from 0 to 4 using
a shared query profile, with checks for relevance, coverage, freshness and
literal operator compliance, as LLM relevance assessors do
\citep{thomas2024llms,upadhyay2025largescale}. The scale adapts the Needs
Met levels of \citet{google2025sqrg}. Ratings 0--4 map to gains
$\{0,0,.117,.667,1\}$; this design choice puts high weight on strong
results \citep{kanoulas2009empirical}. Snippets have a 2,000-character cap.
The studied runs exempt \texttt{site:} queries from duplicate penalties;
Appendix~\ref{app:example} gives the corrected rule.

For each query, the \emph{ceiling} keeps the best rating per normalized
URL across all configurations, variants included, and sorts these ratings,
as in pooled test collections \citep{sparckjones1975pool,zobel1998reliable}.
An engine's \ndcg \citep{jarvelin2002cumulated} uses this list as its ideal. We drop a query-run from
all engines if any judgment fails or no result reaches rating 2.
Appendix~\ref{app:example} gives the formula and an example.

\textbf{Scholar, legal and finance.} Recall@$k$ counts queries with a
matching result in the top $k$. Scholar matches arXiv ids, DOIs and PMIDs;
legal matches citations, dockets and identifiers in URLs and snippets.
Caselaw recall measures case identity, not necessarily the opinion page.
Finance checks whether the snippets contain the answer, with a 0.1\%
money band and a 15\% headcount band. It reads table figures and
parenthesized losses. An LLM may upgrade a non-money miss, but cannot
revoke a hit; a failed backstop judgment excludes an engine's query only
if no result matches. The ceiling is a hit by any engine.
Appendix~\ref{app:finance} checks matcher error.

\subsection{Overall share and failures}
\label{sec:agg}

For bench metric $M_b$, an engine's overall share is
\[
S(e)=\frac{1}{5}\sum_{b=1}^{5}
\frac{M_b(e)}{M_b(\mathrm{ceiling})}.
\]
The benches have equal weight. The ceiling is the best the tested engines
found, not the best the web contains.

Table~\ref{tab:results} uses dashboard scores from the 276 runs in which
all 21 main engines took part. On finance, scholar and legal, account-side
failures (our quota, rate limit, login or credit) are excluded; other
failures score zero. On news and rare, every failure in this window scores
zero. These exclusions remove up to 28\% of an engine's query-runs.
Intervals use run-level bootstraps \citep{efron1993bootstrap} and measure
sampling error, not scorer error. Table~\ref{tab:ci} gives companion
scores with one account-failure policy across all five tasks;
Appendix~\ref{app:examples} maps the scoring protocols.

\section{Results}
\label{sec:results}

\paragraph{Most engine pairs differ, but rank alone is not enough.}
Overall shares span 14.7\% (Ceramic) to 73.2\% (Keenable).
Run-resampled paired tests separate 188 of 210 pairs at 95\%, 178 after
Bonferroni adjustment \citep{carterette2012multiple}, and 164 under both day-level resampling and matched
query support. Only Keenable and Ceramic differ from every other engine
after adjustment. Scholar supplies 3.7 points of Keenable's 4.7-point lead
over Exa; without it the lead is 1.2 points. Appendix~\ref{app:checks}
reports the uncertainty and weighting checks.

\paragraph{Body queries expose gaps that title queries hide.}
Over 31 scholar runs, 23 of 26 configurations reach recall@10 .71--.98
from titles. The same 23 span .08--.72 on body keywords
(Figure~\ref{fig:results}a; Table~\ref{tab:buckets}). Keenable leads at
.72, followed by its realtime mode (.71) and Kagi (.67).
Appendix~\ref{app:scholarpaired} gives paired intervals on common papers.

\paragraph{Weekly ranks are stable, not fixed.}
Adjacent weekly rankings agree at Kendall's $\tau_b$ \citep{kendall1945ties}
.81--.94. Keenable leads all eight weeks, but lower ranks change
(Figure~\ref{fig:results}b). Appendix~\ref{app:checks} checks changes in
the engine pool, account failures and dispatch times.

\paragraph{LLM raters broadly agree with the judge.}
Blinded raters from three vendors grade 1,200 results with quadratic-weighted
$\kappa$ \citep{cohen1968weighted} .90--.94 with one another and .77--.79 with the judge. On 100
complete query pools, two raters each rank engines at Spearman .94 with
the judge, but neither separates Keenable from Exa. These are checks of
model agreement, not human validation. Removing an engine from the ceiling
changes its overall share by at most 0.8 points.
Appendices~\ref{app:validation} and~\ref{app:checks} give the checks.

\section*{Limitations}

\paragraph{Conflict of interest.}
The authors' organization builds an evaluated engine. The code, prompts,
clients and per-query outputs are public so readers can audit the claims.
All engines receive the same queries, snippet cap, request pacing and
judge; each keeps one setting throughout the main window. We cannot tell
whether a vendor changed its index for the benchmark or for other reasons.

\paragraph{Evidence and judge.}
Scores measure the API response, not the fetched page. Short snippets can
hide relevant content \citep{turpin2009summaries,kazai2022less}, and identifier matching can miss a target without
its id. On 400 sampled results, page text changes 25\% of grades. News and
rare depend on one judge; all audit raters are LLMs, and none provides
human validation, which LLM labels cannot replace
\citep{faggioli2023perspectives,clarke2025llmbased}. Shared rules can cause
shared errors. Query-term stuffing can fool judges \citep{alaofi2024fooled};
vendor and model biases can affect scores
\citep{balog2025rankers,soboroff2025dont}. The judge shares a vendor with
ChatGPT search, and a second judge shares one with Claude search; LLM
evaluators can favor their own outputs \citep{panickssery2024self}.

\paragraph{Matcher error.}
Finance table figures can match the wrong period when snippets omit column
headers. A fresh audit confirms only 70\% of table-reading hits; most
others are unresolved, not contradicted. The pooled error estimates cannot
show each engine's error rate. Caselaw recall credits pages about the case,
not just the opinion. Appendices~\ref{app:validation} and~\ref{app:finance}
bound these effects.

\paragraph{Coverage and weights.}
Queries are English and US-centric. Equal bench weights do not estimate
agent traffic, and the lead depends strongly on scholar. Default API tiers
need not be each vendor's best. ChatGPT and Claude search return sources
through answer-generating tools, so their quality scores are comparable
but their latency and cost are not. The ceiling depends on the engine
pool \citep{buckley2007bias}; compare shares within a common window.

\paragraph{Failures and timing.}
Excluding account-side failures assumes those requests would score like
the rest. Without that assumption, several middle ranks remain uncertain.
News and rare also count our credit lapses as zeros in the main window.
Engines process queries at different speeds, so slow engines see news
later. A five-minute dispatch filter leaves the news order unchanged.
Vendor redirect links can break URL matching in later runs.

\paragraph{Repetition and reproducibility.}
Registry facts and the fixed rare stream can repeat. Public sources and
queries permit tuning or special handling of benchmark traffic. The studied
runs archive queries, reference answers, results and judgments, but lack
API publication dates and each run's code revision. Stored ratings reproduce the tables;
re-judging cannot exactly reproduce the inputs. Appendix~\ref{app:examples}
lists the release terms and reconstruction steps.

\subsection{Score sources and failure rules}

Tables~\ref{tab:results} and~\ref{tab:buckets}, Figure~\ref{fig:results}
and the primary paired tests use published
\texttt{data/history.jsonl} from the \texttt{gh-pages} branch. Per-query
checks read archived results and import the repository's scoring code.
\texttt{paper/analysis/manifest.json} lists each result's data, runs,
engines and rules.

The code classifies each failed request with \texttt{account\_side()}.
It excludes HTTP 401, 402, 403, 429, 432 and 433, plus HTTP 400 or API
errors naming credit, usage limits, quota, billing or an API key. Other
failures, including timeouts and server errors, score zero.

The published news and rare scores in the main window count all failures
as zero; per-query checks exclude account-side failures. This raises the
per-query overall base by up to 6.3 points (Claude search). Eleven of the
12 published scholar runs use a different DOI matcher. Finance, scholar
and legal per-query checks nevertheless reproduce every main-window
dashboard row. The later-day news and rare scores exclude every failure.
Table~\ref{tab:protocols} separates these protocols. Table~\ref{tab:ci}
shows the historical overall share beside the consistent-policy estimate;
the latter is not a pure successful-request score, since service failures

\subsection{Rebuilding the results}

Use the backfilled dashboard history revision pinned in
\texttt{analysis/manifest.json}, retaining rows through 11:53 UTC on
29 October 2026. The original history snapshot from that date predates
score corrections and does not reproduce the tables. From \texttt{paper/}:
\begin{quote}\footnotesize
\begin{verbatim}
uv run python \
  analysis/history_snapshot.py \
  history.jsonl
uv run python \
  analysis/table_rows.py \
  history.jsonl table_results.tex \
  analysis/audit/matched_pairs.json
uv run python \
  analysis/adjacent_pairs.py \
  history.jsonl \
  analysis/audit/adjacent_pairs.json
\end{verbatim}
\end{quote}
The commands extract the pinned history, rebuild the main and companion
tables, and rebuild the paired tests. The pinned \texttt{gh-pages} commit
must be present in the local Git clone. Audit scripts, samples and labels are under
\texttt{paper/analysis/}. Repository and dataset revision hashes are
withheld from the text for review and pinned in the release manifest.
The archive supports deterministic re-aggregation of stored labels, not
exact replay of the original judge. Historical API publication dates and
per-run code revisions are irrecoverable; current code cannot restore
them. New judged reports retain publication dates, the query date,
snippet cap and scoring version; CI runs also record the code revision.
A frozen client/prompt configuration and independent human labels remain
requirements for a fully audited future window.

The paired scholar check can run offline from its compact saved hit
records with \texttt{analysis/scholar\_paired.py}; its source and output
paths appear in the manifest. No new API calls or judgments are needed.

\subsection{Data and release terms}

The rare stream draws from DeepResearchGym \citep{coelho2026deepresearchgym}
search logs (59\%, CC BY 4.0; \citealp{ning2026agentic}), OpenResearcher trajectories (39\%, MIT;
\citealp{li2026openresearcher}) and LRAT-Train (1\%, no stated license;
\citealp{zhou2026lrat}). Source terms govern query texts. Our code is MIT;
our CC BY 4.0 covers our results, judgments and metadata, not source text.
The release plan removes LRAT queries without permission. They account
for 113 of 6,901 filtered queries and 17 of the main window's 1,200 rare
query-runs; removing them changes no mean rare \ndcg by more than .003
(\texttt{rare\_drop\_lrat.py}).

Filters reject links, common host names and hash, wallet or vehicle ids,
and cap near-duplicates. A scan of the 1,100 released rare queries finds
no email or HTTP/WWW link, 66 host-like names (61 in \texttt{site:}) and
four long mixed-case alphanumeric tokens. Queries can name people. A
human reads each new query artifact before release. Removal requests can
use private email to the release contacts in the repository README;
requesters should not post personal query text in public issues. We publish API titles, URLs and snippets
as evaluation records under our reading of vendor terms and withdraw an
engine's archived outputs on request.

\section{Query Filters and Scoring Details}
\label{app:leak}

\subsection{Query filters}

Scholar balances five domains (computer, physical, life, social and health
sciences) and three age bands (7 days, 30 days, 1 year). Each paper must
pass all four query filters:
\begin{itemize}[nosep,leftmargin=1.2em]
\item \textbf{Title:} at least four words, plus a digit, acronym,
  hyphenated term or five content tokens.
\item \textbf{Body keywords:} at least three words and two content
  tokens absent from title and abstract.
\item \textbf{Body question:} at least eight words and the same novelty
  test as body keywords.
\item \textbf{Tip-of-tongue:} at least twelve words; no quotes, decimal,
  five-digit number or coined title/abstract term; at most two content
  tokens shared with the title.
\end{itemize}
An instrumented run accepts 323 of 572 candidates (56\%); domain rates
range from .41 to .73. Each domain--age cell takes its first seven accepted
papers. The effect of rejecting other papers on engine order is untested
(\texttt{scholar\_rejects.py}).

News draws from 124 feeds and Google Trends RSS for 52 US geographies.
Legal caption queries use opinions from 14 federal courts on CourtListener.
Sources include \url{trends.google.com}, \url{api.gleif.org},
\url{data.sec.gov}, \url{courtlistener.com} and \url{ecfr.gov}.
Rare queries must pass fastText English language ID
\citep{joulin2017bag,joulin2016fasttextzip} and contain a word split into
at least five BERT WordPieces \citep{wu2016gnmt,devlin2019bert}.

A CFR query needs at least three words and exactly one verbatim span of
two to eight words. It must not contain a citation form (CFR, U.S.C.,
\S, ``section $n$'', ``title $n$'') or the target part or section number.
Only the quoted variant retains quotation marks. News prompts reject
evergreen items and request a two-to-six-word query about the event.
Table~\ref{tab:examples} shows sample queries.

\subsection{Judge profile and checks}
\label{app:judge}

A profile call sees the query and run date. It returns the query type
(broad, specific or list), domain, operators, one to three main aspects,
auxiliary aspects and a content type (ephemeral, persistent or evergreen).
Aspects describe required content, not the answer. Every result uses the
same stored profile.

The result call sees that profile, the run date, title, URL, API publication
date if available, and snippet. It emits eight checks and a 0--4 rating:
integrity, relevance, main-aspect coverage, list completeness, event
freshness, staleness, a domain cap and operator compliance. Failed relevance
or operator compliance forces 0; failed coverage or completeness caps the
rating at 2. Staleness lowers ratings by one or two levels, or to 0 for a
wrong year or entity status. A dated-event result about the entity but not
the event is capped at 1. Quotes must appear verbatim in the title or
snippet; \texttt{site:} must match the URL host. The judge must use the
result's text and authority, not its own answer knowledge.

Ratings 0--1 mean Fails to Meet, 2 Slightly Meets, 3 Highly Meets and 4
Fully Meets. The scale has no Moderately Meets level, and rating 4 does not
need the single-answer intent that the guidelines require for Fully Meets
\citep{google2025sqrg}. Prompts live in \texttt{src/needle/shared/prompts}.

\subsection{Ceiling and worked example}
\label{app:example}

For ratings $r_i$ and gains $g(4)=1$, $g(3)=.667$, $g(2)=.117$,
$g(1)=g(0)=0$,
\begin{gather*}
\mathrm{DCG}_e(q)=\sum_{i\leq5}\frac{g(r_i)}{\log_2(i+1)},\\
\mathrm{nDCG}_e(q)=\frac{\mathrm{DCG}_e(q)}{\mathrm{IDCG}(q)}.
\end{gather*}
IDCG is the DCG of the top five pooled ratings, keeping the best rating
per normalized URL. A bench metric is the mean over scored query-runs;
the judged ceiling has mean 1. A shorter returned list gets no padding.

For example, A returns ratings 4 and 2; B returns 3 and 4, with the
4-rated URL shared by both. The pooled ratings are 4, 3, 2, so
$\mathrm{IDCG}=1+.667/1.585+.117/2=1.479$.
A scores $(1+.117/1.585)/1.479=.73$; B scores
$(.667+1/1.585)/1.479=.88$.

URL normalization removes tracking parameters. The historical scorer
exempts \texttt{site:} queries from duplicate penalties. That exception
affects 3 of 1,748 rare \texttt{site:} engine--query pairs in the main
window and can produce \ndcg above 1, so the pooled ideal is not a strict
upper bound for those records. The corrected scorer
(\texttt{ndcg-dedup-all-v1}) gives every repeated normalized URL zero gain,
including on \texttt{site:} queries. The historical tables retain their
stored scores; they do not mix this correction with old results.

\subsection{Finance matching rules}

Money must fall within 0.1\% of the reference value; headcounts within
15\%. A scale word fixes a money figure's scale. A bare figure, including
a parenthesized loss, can mean thousands or millions only if the preceding
200 characters contain \$, USD, dollar, millions, thousands, revenue,
sales, income, loss, earnings, profit or EPS. Years, percentages and
multiples do not qualify. Diluted EPS also needs EPS, ``per share'' or
``earnings per'' in the result. No money result gets an LLM backstop.
Other fields can receive an upgrade, never a revoked hit. A known-item
hit counts on any host, even for \texttt{site:} queries; this differs from
the judged benches' literal operator rule.

The rules live in \path{src/needle/finance/canon.py} and
\path{src/needle/shared/search/errors.py}. Appendix~\ref{app:finance}
checks their error rates.
