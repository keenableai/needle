NEEDLE: Which search API moves the needle for AI agents?

News runs hourly; all other suites run daily. Times are UTC.

NEEDLE (News, Everyday, Expert, Deep-tail, and Legal Evaluation) is an agentic search benchmark that compares major search engines using queries modeled on real agent behavior. We include five verticals that mirror the use cases we see every day in Keenable's own search traffic:

  • News: breaking and developing stories that people are asking about right now, generated hourly from roughly 124 curated RSS feeds and Google Trends
  • Finance: everyday company and SEC-filing lookups, with known answers drawn from Wikidata, GLEIF, and SEC XBRL
  • Scholar: expert literature searches; the task is to find a specific paper from a degraded title, a full-text detail, or a tip-of-the-tongue description (inspired by Exa's publication-search evals)
  • Agentic rare: obscure, long-tail entities; rare-word queries sampled from the DeepResearchGym agentic search logs (Agentic Search in the Wild, SIGIR '26)
  • Legal: find a specific court opinion or section of the Code of Federal Regulations

We regenerate the known-answer sets (finance, scholar, and legal) daily from public sources. About half of the finance and legal queries use search operators such as "…", site:, and after:.

We send every engine the same query at the same time, one request at a time, and score it blind on its results exactly as returned. We exclude failed searches and judgements from the averages instead of counting them as zero. The full comparison protocol is in the appendix; we maintain the benchmarks in keenableai/keenbench.

Metrics

Each vertical reports one headline metric; which one depends on whether a query has a single known answer.

Open-ended (news, agentic_rare): our LLM judge scores every result from 0 to 4; the headline metric is nDCG@5: discounted cumulative gain over the top 5 results, normalized by the ideal ranking of every engine's pooled results, so ultimate scores exactly 1. We penalize duplicate URLs and repeated domains.

Known-answer (finance, scholar, legal): we check whether the target answer appears in the top 5 (finance, legal) or top 10 (scholar), and report mean reciprocal rank (MRR) for how high it ranked. Charts show seven-day rolling averages.

The ultimate ceiling: we also score a synthetic engine that pools every engine's results per query and ranks them oracle-style (full definition in A2). It appears as the italicized row in every leaderboard, and the standings radar plots each engine as a share of it.

Index independence

We send every engine identical queries, so we can compare returned URLs directly across engines. Independent engines will naturally overlap on canonical, relevant results. Repeated overlap on low-relevance URLs or near-identical result lists instead suggests a shared upstream index.

Suspicious sharing measures these cases. The borrowing graph estimates the likely direction of sharing, while URL overlap, 3+ shared, and the uniqueness tables provide the underlying similarity measures. All views use runs from the previous two weeks, across all benchmarks.

Definition: suspicious sharing

the pairwise test behind the matrix and the borrowing graph (src/keenbench/shared/overlap.py)

Let UA(q) be the normalized URLs engine A returned for query q, and LA(q) ⊆ UA(q) those judged below HM. Engines A and B share suspiciously on q when

|LA(q) ∩ LB(q)| ≥ 1 or |UA(q) ∩ UB(q)| ≥ 3.

Each matrix cell is the share of comparable queries (both searches succeeded and at least one returned a result) on which the pair shares suspiciously, pooled over all runs from the last 2 weeks. Sharing good results is how ranking is supposed to work; sharing junk, or 3+ URLs at once, suggests a common upstream index. On the known-answer verticals results carry no judgements, so only the second clause can fire.

Appendix — methodology & configuration

We pin everything below in keenableai/keenbench; the dashboard only aggregates published run data, and you can recompute every number on this page from the archived artifacts (A6).

A1 — query generation

how we build each slice's queries (per-bench generate.py in the repo); we archive the exact query rows every run used with it (A6)

We generate every query set fresh from public sources: news hourly, the other verticals daily. For scholar we sample papers from arXiv (computer, physical, life, and social sciences) and Europe PMC (health sciences) over four age bands reaching from the last week back to roughly five years. Each paper yields one query per slice, so the four scholar slices rank engines on the same papers, and the gaps between slices are the point: title vs body isolates full-text indexing, body vs clue isolates keyword-vs-prose handling, and tot isolates semantic retrieval. We leak-check the LLM-written scholar queries (at least two content words must not appear in the title or abstract) and keep a paper only if every slice produced a valid query. We modeled the known-item and tip-of-the-tongue framing on Exa's "SOTA Search Over Academic Publications" (Jul 2026). The agentic_rare stream is the anonymized DeepResearchGym log release (14.44M search requests from real agentic clients) published with "Agentic Search in the Wild: Intents and Trajectory Dynamics from 14M+ Real Search Requests" (SIGIR '26).

A2 — comparison protocol

the fairness rules behind every number on this page

We send every engine in a run the identical query text at the same moment, with the per-engine request shapes pinned in git (A5). Each engine issues one request at a time, so latency percentiles are comparable across engines rather than reflecting different concurrency.

We judge an engine on its own ranking, titles, and snippets, with no fetching and no re-ranking. We cap evidence at the same snippet length for every engine, so engines that return fatter content get no extra signal to the judge or the answer matchers. We judge results with the same URL once across engines and share the rating, so formatting differences cannot split a judgement (A4 has the full judging setup).

We exclude failed searches and judgements from the mean and report them through search_errors and judge_errors. An outage therefore reduces num_scored and raises the error rate without lowering the quality score.

We mint fresh news queries every hour and regenerate the known-answer verticals daily from public sources (A1), so there is no fixed benchmark set to overfit. We archive the exact queries each run used with it (A6).

Every vertical also reports ultimate, a synthetic engine that pools all engines' results per query and ranks them oracle-style: best judge rating first (redundancy-aware) on the judged verticals, the gold item first on the known-answer ones. Its score is what a single engine would achieve if it always returned the best of what the whole field found, separating "the engine ranked poorly" from "nothing better was findable". We exclude it from the overlap and uniqueness statistics.

A3 — metric definitions

how we compute every number on this page (src/keenbench/shared/metrics.py and per-bench score.py)
metricbenchesdefinition
nDCG@5news, agentic_rare DCG over the top 5 results (Σ gain(rᵢ) / log₂(i + 1), with judge ratings mapped to gain 4 → 1.0, 3 → 0.667, 2 → 0.117, 1/0 → 0), divided by the DCG of the ideal ranking: the pooled ultimate ordering of every engine's deduplicated results, so ultimate scores exactly 1. A query is scored only if every one of its results was judged (otherwise it is dropped from the mean and counted as judge errors) and only if the pooled ideal has any gain; queries where no engine found anything relevant are excluded.
redundancy penaltynews, agentic_rare applied to ratings before scoring, on the engine and ideal sides alike: a duplicate URL −4 rating steps, the 2nd result from the same domain −1, the 3rd and later −2, all floored at 0. Skipped when the query itself carries a site: operator. Raw and penalized ratings are both shown in the judgement browser.
answer-recall@5, MRR@5finance a query is a hit when the gold answer appears in a top-5 title or snippet (deterministic matcher, with an LLM-judge backstop for paraphrased answers). MRR is the mean reciprocal rank of the first hit.
recall@10, MRR@10scholar known-item: the gold paper identified in the top 10 by arXiv ID / DOI / PMID match.
recall@5, MRR@5legal known-item: the gold opinion or CFR section identified by citation / docket / URL match.
latency p50 / p95all percentiles over per-call durations of successful search API calls, pooled across queries in the window; runs published without per-call samples contribute their per-run percentiles instead. Failed calls carry no latency sample and show up in the error rate.

A4 — LLM judge

rates news and agentic_rare results; we use it for finance only as a fallback answer matcher, and judge scholar and legal deterministically

We judge with openai/gpt-5.6-sol via OpenRouter, temperature 0, one pointwise call per document. We record the exact model a run used as judge_model in its archived report and show it when you pick a run in the judgement browser, so judge swaps are visible in the history.

The judge is blind to engine identity: the prompt contains the query, document title, URL, published date, and snippet, never the engine name. We pool results with the same URL from different engines, judge them once per query (longest available snippet, first non-empty title and date), and reuse that single judgement for every engine that returned the URL, so an engine cannot gain from formatting the same page differently. Snippet quality still matters across distinct URLs: a judge preference for a snippet style would be a shared bias across engines. We publish the per-result reasoning with every run so this can be audited.

Rubric: 0–4 Needs Met scale (FailsM / SM / HM / FullyM) with hard gates for wrong entity, stale coverage of dated events, and search-operator compliance ("quoted phrases", site:). The full prompt is one template in the repo: src/keenbench/shared/prompts/judgement.jinja.

Known limitation: we operate NEEDLE ourselves and have not yet run a systematic human-agreement audit of the judge. What makes the numbers checkable in the meantime: the judge is blind and shared across engines, every rating ships with its reasoning, and we publish queries, prompts, and raw results, so anyone can independently re-score any rating.
